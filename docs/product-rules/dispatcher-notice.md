# 派发方通知：伙伴开的任务停下时由宿主告诉伙伴

> **读取时机**：新增或修改「任务停下后通知派发它的对话」的判定、内容、投递、去重与上限，或改动它依赖的活动状态、输入来源标记之前
> **适用路径**：`apps/desktop/src/main/dispatcher-notice/**`

本文件是个人分支（fork）的产品裁决，不是上游规则。上游 2026-11-09 起的规则是「宿主不替任务回传结果」，
回传由派活方在交代里请对方发回；本 fork 的主人 2026-11-25 裁决改为宿主发事件，原因是任务出错、被打断或
Agent 起不来时，任务里的 Agent 根本没有机会回信（一次事故里伙伴开的任务出错后 5 个多小时无人知道）。

## 规则

- **关系常驻**：伙伴（或任何任务）用 `send_to_session` 在本机新建任务时，宿主记下「派发方 → 任务」，直到任务归档或删除。
  不需要伙伴写参数，也不需要在交代里要求任务回信。
- **谁的请求**：一轮处理过的输入里只要有派发方发来的消息（发送方是伙伴的对话，或就是这件任务的派发方），这一轮就归派发方；
  主人中途插话不改变归属，通知里注明「用户也发过消息」。只有主人输入（以及定时任务、插件、普通任务之间互发）的轮次不通知。
  依据只有宿主写在消息上的来源标记（`agent_meta.origin`），不看正文。
- **跟住宿主续跑**：出错后自动重试、Cindy 重启后接着做、用量恢复后继续，都沿用上一轮的归属，直到任务真正停下
  （不在跑、没有挂起交互、没有排着的续跑、队列里没有可执行的消息；暂停的队列和等人点「重试」的出错横幅都算停下）。
- **什么时候发**：
  - 完成、出错：真正停下时发一次；出错要等宿主放弃自救后才算。
  - 重启时被打断：Cindy 启动后扫描还挂着请求的任务，上一轮没收尾且宿主没有排续跑时发一次。
  - 投递前就失败：派发方的消息在开始处理前失败（输入协调器的出错横幅指向这条消息）时发一次。
  - 等待（提问、让选选项、等计划确认、等权限审批）：立即发，同一次等待只发一次。
  - 主人手动停止：不发，静默结清。
- **等待的内容**：提问类带问题原文和全部选项（每题 ≤500 字、每个选项 ≤120 字、整条 ≤1500 字）；计划确认只说在等确认，不带计划正文；
  权限审批只写工具或操作名，不带参数，并写明「只有用户本人能在任务里批准，伙伴不能代批」。任何通知都不带代输入的值。
  派发方不能替用户批准权限或确认计划。
- **派发方的回复就是回答**（2026-11-25 主人裁决：通过宿主实现，不给伙伴加新工具）：任务停在由这位派发方的请求引出的
  提问上时，派发方之后用普通的 `send_to_session` 发给这个任务的下一条消息，由宿主当作对这个提问的回答交进去
  （与主人在卡片里作答同一条宿主通路），而不是排在队列里等人点卡片。通知里写明这一点，`send_to_session` 的回执带
  `answered_question: true`。按选项名（忽略大小写）或序号匹配；多选题按逗号拆分；多道题按「1. … 2. …」逐行写时
  逐题作答，否则每道题都交整段回复；对不上的部分按卡片里的「其他」手打文字处理。题目限定只能从固定选项里选而回复对不上时
  不作答，消息照常排队，回执告诉派发方可选的选项。只转接提问类，且只转接通知过这位派发方的提问；权限审批、计划确认、
  代输入永远不这样处理，别的对话发来的消息也不转接。远程派发方第一期不转接。
- **主人先处理了等待**：通知还在派发方队列里没被处理，就撤回；已经被处理过的，补一句「已由用户处理」。
- **任务已自己回信**：这串请求期间任务已用 `send_to_session` 发回派发方，就不再发「完成」；出错、等待照发。
- **合并**：派发方忙时通知进它的输入队列（不插话），同一任务后来的通知替换队列里还没被处理的旧通知。
- **不设上限，只防来回空转**（2026-11-25 主人裁决）：不按天限量，正常通知一条都不吞。只在「派发方与任务连续来回、
  期间主人在任务里和派发方对话里都没说话」达到设定次数时暂停这件任务的通知：给主人发系统提醒（桌面 + 手机），
  给派发方发最后一条「已暂停」；主人在任一边说话后自动恢复。次数在账号数据目录 `dispatcher-notice/settings.json` 的
  `loopPauseAfter` 配置，默认 30，`0` 关闭。没有这层保护时最坏情况是两边一直轮流跑、每个来回各耗一整轮模型用量，
  直到有人发现或用量耗尽。
- **派发方不可用**：派发方对话已归档、删除，或它所属的伙伴不在用，改给主人发系统提醒（桌面通知 + 手机推送），不恢复那个对话。
- **跨电脑**：第一期只处理本机派发方。派发方记成「电脑 + 对话」，投递只经一个入口；远程派发方的消息暂不建立归属，第二期接远程通道。

## 通知的身份

通知以「由任务「X」发送」的普通来信进入派发方对话（`origin.kind = 'session'`，发送方是这件任务），正文第一行写明
「Cindy 宿主发出，不是用户输入，也不代表用户授权」，自动审核身份按「不是主人原话」处理。

## 实现

- 纯逻辑：`core.ts`（归属、续跑跟随、停下判定、去重、合并、上限）、`classify.ts`（来源标记归类）、
  `noticeText.ts`（正文）、`pendingInteraction.ts`（挂起交互的最小内容）、`answerRouting.ts`（回复→提问回答）。
- 存储：`store.ts`，每件任务一个小文件，账号隔离的用户数据目录，跨进程锁 + 原子写，坏文件跳过。
- 宿主适配：`service.ts`；Desktop 装配 `desktop.ts`；`register.ts`／`mcp-providers.ts` 只依赖轻量的 `hooks.ts`。触发源是灵动岛的规范活动变化（主进程，灵动岛关掉也照常产生）
  与输入协调器的投影；`register.ts` 只安装一个最小宿主桥，`mcp-providers.ts` 在 `send_to_session` 成功后记关系与「已自己回信」。
