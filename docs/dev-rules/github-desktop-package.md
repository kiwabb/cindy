# Personal Mac builds and updates from GitHub

The approved publisher is `kiwabb/cindy`, with `main` as its sole release source. The Mac workflow builds the Global Apple Silicon client through the existing `release:package` command and official packaged startup/database smoke test. It creates a verified DMG for manual installation and a ZIP for the personal update channel.

## Build and download

A push to `main` builds automatically. A manual **Actions → Package desktop for Mac → Run workflow** must also select `main`. Disable **Publish the tested app to GitHub Releases** for an artifact-only build. Other repositories and branches cannot publish this channel.

Each update uses `github.run_id * 100 + github.run_attempt` as its positive safe-integer revision. Attempts 100 and above, arithmetic overflow, a dirty source tree, mismatched source identity and skipped smoke all fail the personal build. The display version remains `0.0.0`. The independent personal revision orders updates.

Download `cindy-unversioned-arm64.dmg` from a revision release for a first manual installation. Open the DMG and drag `Cindy.app` to Applications. An existing personally signed installation uses the personal updater to preserve its Apple identity. The run also retains its artifacts for 14 days. Installed profiles remain separate from source-development sandboxes.

A successful main-branch Actions package and official smoke job can also supply the first bootstrap while a publisher repair is pending. Verify its actual run source, artifact digest, inner ZIP hash and embedded build/storage identity. Re-sign on the owning Mac and run the official isolated smoke before installation. Record the successful package job and failed publisher separately, including that the bootstrap artifact has not entered the public feed.

## Personal update publication

`apps/desktop/personal-update-channel.json` fixes the repository, channel and feed URL. The shared validator in `src/main/personal-update/contract.mjs` is used by both producer and client.

1. Package a clean committed checkout, verify its embedded `cindy-source.json` identity, run the official smoke test and hash the ZIP.
2. Extract that ZIP for DMG creation and verify its actual source metadata again. Generate `personal-update.json` and `SHA256SUMS` from those bytes.
3. Create `personal-macos-arm64-r<revision>` as a draft, upload all assets and verify every remote asset's SHA256 and size. Publish the immutable release and verify the actual Git tag resolves to its source commit. Keep it outside GitHub's general latest release. Retries may complete a draft but cannot overwrite existing immutable bytes.
4. Recheck the current channel revision, persist and verify the revision floor in the separate `personal-macos-arm64` release notes, then replace its single manifest asset. Verify the published manifest after upload. All Mac workflow runs share a serialization group. A higher existing floor or manifest revision stops an older run. A missing asset can be repaired at the same revision using the verified immutable release.

GitHub REST release-by-tag returns published releases. Keep the ID returned by draft creation and refresh drafts by ID. Recovery searches every release-list page for the exact tag and rejects ambiguous IDs or invalid publication state. Only a documented duplicate-tag conflict may reuse an existing draft. Asset verification and actual published-tag commit verification must finish before the channel advances. Unit API fixtures must model unpublished drafts with no by-tag result or Git ref. [GitHub release API contract](https://docs.github.com/en/rest/releases/releases#get-a-release-by-tag-name)

The feed is `https://github.com/kiwabb/cindy/releases/download/personal-macos-arm64/personal-update.json`. The general GitHub latest release can belong to Windows and is not an update input. An immutable release left behind by a failed channel publication is safe to retry. GitHub asset replacement can briefly return 404, so clients retain the installed app and retry later.

A failed personal update check defers installation and retains verified cached bytes until a successful check confirms the same revision, source and storage identity.

The manifest records `schemaVersion`, `repository`, `channel`, `revision`, `sourceCommit`, `platform`, `arch`, `region`, `bundleIdentifier`, `storageIdentity` and `asset` (`url`, `sha256`, `size`). The signed app's `cindy-source.json.personalUpdate` carries the same identity without the self-referential ZIP asset. `build-info.json.personalUpdate` mirrors that identity. A source commit alone cannot describe uncommitted feature files, which is why personal-channel builds require clean committed source.

## Storage compatibility and signing

`storageIdentity` hashes migration runtime resources, the schema source, personal-todo JSON persistence and the policy's explicit `storageCompatibilityVersion`. Personal-todo coverage includes `personalTodoStore.ts`, its underlying `botTodoStore.ts` and the shared `teammateTodo.ts` representation. Development-only numbered Drizzle snapshots are excluded because packaging removes them. Changes to these inputs conservatively block automatic replacement. Raise `storageCompatibilityVersion` for incompatible changes to other persisted formats, including preferences and credential envelopes. The client requires identical installed/candidate storage identities before automatic replacement.

CI produces an ad-hoc-signed payload. The owning Mac prepares it with its existing Apple Development signing identity before installation. Private keys and local identity configuration stay on that Mac. Automatic installation waits for idle work and preserves the previous app for failed-start recovery. Storage incompatibility stops automatic installation. App rollback does not establish that a database migration can be reversed.

For a one-time operator repair, a private copy of a verified CI app may receive only the native monitor helper rebuilt from the exact reviewed, merged `main` source and production compiler flags. Keep its base CI identity and ASAR unchanged. Record the base identity, merged repair commit, C-source digest and final signed helper digest in a sealed `cindy-local-repair.json` resource. Preserve the helper identifier and main entitlements; sign the helper, record its digest, then reseal the App without changing the helper again. Verify the original designated requirement, strict signatures, unchanged ASAR/source metadata and official isolated smoke before a normal-quit atomic installation with the pure CI app retained for rollback. This is an explicitly recorded local bootstrap, not a CI-produced app. Its next update must still use a higher genuine published CI revision and the unchanged runtime validation, transaction and health gates. Failed revision markers remain intact.

The detached transaction monitor clears its own inherited Crashpad task/thread exception ports before acquiring its lease or acknowledging startup. Isolation failure stops the update before the App quits; the main App retains its crash handler. The monitor still waits for every live canonical-bundle process, including Crashpad. It does not ignore or terminate a live handler.

The personal installer requests the existing normal quit lifecycle after its transaction is acknowledged. Runtime, browser, remote-service and database cleanup runs through the existing bounded disposer chain before exit, with the existing shutdown watchdog. The monitor waits for the old PID identity and every live executable inside the canonical bundle. Zombies and reused outside-bundle PIDs do not block, while real sibling instances and unknown matching process state remain blockers. Failed waits retain their phase/reason and a bounded PID/PPID/birth/state/relative-executable diagnostic in the owned attempt directory. The diagnostic excludes argv and environment values.

The upstream official feed remains disabled for the `0.0.0` community version. This separately approved personal channel provides its own source, revision, storage and signature checks. Public ad-hoc downloads are not notarized. macOS can block their first manual launch. After attempting to open a trusted download, use **System Settings → Privacy & Security → Open Anyway** if offered.

The producer unit tests cover revision bounds, storage identity changes, ZIP/source mismatches, publisher restrictions, publication order, retry, remote corruption, racing channel revisions and authentication failures. Record whether the bootstrap is a genuine CI artifact or an explicit operator repair; neither replaces acceptance of a higher genuine published revision through the installed updater. Record automatic discovery/preparation, idle eligibility and the actual installation trigger separately. An explicit update-now request uses the normal manual entry while retaining the configured idle auto-install preference.

## Personal signing on one Mac

For a stable local identity across personal builds, run `pnpm release:package --platform darwin --arch arm64 --local-sign` on the owning Mac. This also signs versionless `0.0.0` builds and produces an app ZIP. It uses public metadata at `~/Library/Application Support/CindyLocalSigning/identity.json` with `schemaVersion: 1`, `certificateSha1` (the dedicated code-signing certificate's 40-character SHA-1 fingerprint) and `keychainPath` (the absolute path of the user's login keychain). Create a self-signed certificate through macOS Keychain Access or an Apple Development certificate through Xcode's account settings before building. Its private key stays in that keychain under macOS access control.

Existing schema-1 metadata defaults to self-signed mode, which binds each nested code object to its identifier and the exact certificate. For a verified Apple Mac development identity, add `signingKind: "apple-development"` and the public 10-character `teamId` to the same metadata. This mode uses `certificateSha1` only to select the current signing key.

The Apple development designated requirement binds each object identifier to the genuine Apple chain, WWDR intermediate, Mac development certificate type and TeamID, allowing certificate renewal within that team. The signer verifies the actual Apple requirement and observed TeamIdentifier on every signed object.

| Configuration or validation case | Result |
| --- | --- |
| Schema 1 with omitted kind or `self-signed` | Preserve the existing identifier and exact-leaf requirement. |
| `apple-development` with a 10-character uppercase alphanumeric string `teamId` | Require the Apple chain, WWDR intermediate OID, Mac development leaf OID and matching TeamIdentifier. |
| Unknown kind, or `apple-development` with a missing, numeric or array TeamID | Reject configuration before signing. |
| Self-signed certificate with a matching OU, wrong Apple team or failed chain validation | Fail strict signature verification and stop packaging. |
| Renewed Apple development certificate for the same team | Update the certificate selector and retain the team-bound requirement. |

Signing uses no timestamp server or notarization. Retain the same certificate and private key for future self-signed builds. `--local-sign` conflicts with `--no-sign` and rejects `--version`, keeping these personal builds on the community `0.0.0` update policy. Without the local flag, existing signing selection applies. The local metadata, certificates, private keys and keychain passwords belong outside the repository. The exported `signLocalMacApp` in `apps/desktop/scripts/ci/local-mac-signing.mjs` also signs an existing personal app copy with the same policy.

The local build first checks the pinned public certificate using macOS's `codeSign` trust policy. In self-signed mode, a failed check requires the owner to explicitly confirm code-signing trust for that dedicated certificate in Keychain Access. In Apple development mode, check the certificate's validity and matching WWDR intermediate chain, with Apple certificate trust settings at their system defaults. The build checks trust through the public certificate. Local packaging runs the existing packaged smoke test after final signing and before creating the ZIP, subject to `--skip-smoke` and the existing unsupported-host-architecture skip.

Verify signature integrity and identical designated requirements on two distinct builds, then check real Accessibility authorization after replacing the first build with the second. Unit checks cover legacy metadata, invalid types, renewal-stable requirements, strict Apple validation before TeamIdentifier comparison, and smoke-runner selection. Permission continuity requires this native upgrade check.

A stable self-signed designated requirement does not guarantee uninterrupted Keychain access across builds. Apple's public Security implementation assigns a `cdhash:` partition identity to signed code outside its recognized Apple and developer signing categories. A changed CDHash can therefore require renewed Keychain access confirmation despite an unchanged certificate and designated requirement. The specific Keychain ACL and partition state on the tested Mac were not inspected. See [Apple's `partitionIdForProcess` implementation](https://github.com/apple-oss-distributions/Security/blob/main/securityd/src/clientid.cpp#L187-L287).

In the local two-build trial, both builds passed strict signature checks with the same leaf-bound requirement and different CDHashes. The second build stalled in Keychain credential access during isolated smoke and normal startup at the same Applications path. Restoring the first build recovered the account UI and microphone and automatic-input authorization. Native upgrade acceptance must include successful existing-login credential decryption, entry into the main UI, and retention of prior permissions. Preserve failed smoke results and resolve their cause before accepting an upgrade. Do not bypass this acceptance with `--skip-smoke` or broader Keychain ACLs.

The subsequent Apple Development trial used two copies of the existing functional app with different bundle build numbers and CDHashes. Both passed the official isolated startup and database smoke test. After initial Keychain, microphone and Accessibility consent for the Apple identity, replacing the first build with the second at the same Applications path entered the existing account UI and retained microphone and automatic-input authorization without another consent prompt. These local signing checks cover the signing identity. Acceptance of the personal feed additionally requires a genuine tested CI bootstrap followed by a higher published CI revision applied through the installed updater.

CI validates packaged startup and database access. A successful build does not establish real account login, model calls, native permissions, or device connectivity on the user's Mac.

The first natural personal-update trial passed automatic discovery, download, local signing, official smoke and the ten-minute idle gate. Its old client then bypassed the normal quit lifecycle, and the full-bundle wait timed out before exchange. The monitor marked that revision failed and reopened the prior app. The user subsequently requested immediate installation, completed by normal lifecycle shutdown and manual atomic exchange with the same verified signed ZIP. That manual result is separate from a successful automatic transaction. A subsequent repaired-controller trial completed normal quit but stopped before exchange because a live Crashpad handler remained; its process diagnostic and failure record were preserved. At publication of the monitor-isolation repair, a subsequent genuine target and runtime health receipt were still pending.
